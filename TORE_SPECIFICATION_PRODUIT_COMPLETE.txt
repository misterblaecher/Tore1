PARTIE 1 - VISION & ARCHITECTURE

1. Vision stratégique
- TORÈ est un OS opérationnel territorial pour la guindaille liégeoise : bars, comités, événements, folklore.
- Objectif produit : devenir **indispensable** (workflow terrain), **non substituable** (dépendances + mémoire),
**audit-able** (ledger + logs).
- Postulat terrain : bruit, pénombre, rush, réseau instable, staff fatigué, public alcoolisé ? UX "zéro réflexion".
- Principe : warnings + plafonds + responsabilités explicites plutôt que blocage arbitraire.
- Principe : **un seul point d'entrée** = Scanner QR universel, qui route vers le bon module.

2. Architecture modulaire
- Les entités (Bar, Event, Comité, Groupe) activent/désactivent des modules indépendants.
- Module = UI + API + règles + logs + exports.
- Dépendances explicites : certains modules nécessitent d'autres (ex: Orders nécessite Menu; Bets nécessite Wallet ou Tickets).
- Modes: **USER app** (expérience soirée), **Staff/ORGA app** (opérations terrain), **Portail Web** (ops & admin),
**Admin Global** (sécurité/abuse).

3. Modules ON/OFF
- État module: OFF (invisible côté USER), ON (actif), FROZEN (visible mais actions bloquées), READ_ONLY (consultation).
- Toggle gouverné par permissions serveur; toute bascule génère un log signé.
- OFF côté USER = disparition totale (pas de placeholder).
- Règle de priorité : l'**Event State** peut forcer READ_ONLY/FROZEN même si module ON.

4. Ledger append-only
- Toute valeur (tickets, top-up, gifts, refunds, payouts, bets, ardoise) est écrite dans un ledger append-only.
- Une correction n'efface jamais : elle écrit une transaction inverse (compensating entry).
- Chaque entry: id, entity_scope, actor_id, action_type, amount, currency_unit, reason_code, reason_text, refs (order_id/bet_id), timestamp, signature.
- Exigences: idempotence (anti double), ordering stable, exportable CSV/PDF, vérification signature.

5. Scanner QR universel
- Un seul composant scanner (mobile) route vers : join event, menu, order confirm, staff entry, staff bar, bet, hunt, wifi, safe kit.
- QR sensibles signés + expiration + anti-replay + binding context (event_id/bar_id).
- QR non sensible (ex menu public) peut être non signé mais versionné.
- Fallback: saisie code manuel, et écran "QR inconnu" (support + diagnostic).

6. Mode réseau faible
- Caches : menu, infos event, modules actifs, derniers prix, consignes.
- Politique actions :
- Non sensibles ? queue locale (ex: log local, check-in boisson) puis sync.
- Sensibles valeur/accès ? bloquées si backend down (sauf règles explicites ORGA).
- UI doit exposer: ONLINE / DEGRADED / OFFLINE, avec message actionnable.

7. Architecture multi-tenant (comités isolés)
- Séparation stricte : committee_id est clé de scoping pour données comité (forum, baptême, finances).
- Cross-tenant interdit par défaut; exceptions : Admin Global, statistiques anonymisées, marketplace de bars.
- Contrôle d'accès : ABAC/RBAC hybride (role + scope + module + event_state).
- Rétention et exports RGPD : suppression user, anonymisation logs (selon obligation légale), export complet.

PARTIE 2 - STATE MACHINE GLOBALE

0. Table de priorité des états (global)

| Priorité | État | Scope | Effet UI | Effet API |
|---|---|---|---|---|
| P0 | SECURITY_LOCKDOWN | Global | Tout en lecture seule sauf Admin Global | Refus actions sensibles + exigences raison |
| P1 | BACKEND_DOWN | Global | Bannières offline + routes limitées | Read endpoints cacheables only |
| P2 | EVENT_CLOSED | Event | Event Hub en mode recap | No new orders/bets/entry; exports allowed |
| P3 | EVENT_PAUSE | Event | Actions gelées + message orga | Queue ou refuse selon type |
| P4 | NETWORK_DEGRADED | Device/Event | UI simplifiée + refresh réduit | Backoff + fallback cache |
| P5 | MODULE_FROZEN | Module | CTA désactivés + raison visible | Write endpoints de module refusés |
| P6 | MODULE_ON | Module | Normal | Normal |

Contrats d'interface (API) - invariants transverses
- Tous les endpoints write requièrent: `X-Idempotency-Key`, `actor_id`, `scope`.
- Tous les logs critiques requièrent: `reason_code` + `reason_text` quand sensible.
- Timestamp serveur authoritative; device time seulement informatif.
- Toute action bloquée doit renvoyer: code erreur, message UX court, et `next_allowed_actions`.
